# Install and use the VPN system, step by step

This guide covers the **management development candidate**, not the older
published v0.4.1 dashboard. PR #5 is still awaiting its remaining browser checks.
Use a separate test Linux server first. This guide does not approve deployment
over an existing production VPN.

## 1. What does it do?

Imagine your Linux server has several roads to your office. These roads are VPN
tunnels. You choose their order. The service checks them and sends office traffic
through a working road. A preferred road must remain healthy before it is used
again. Public internet traffic and public SSH keep their existing default route.

The engine moves traffic. The dashboard lets you see it, prepare settings and,
when explicitly enabled, request guarded changes. You do not install this
container on a MikroTik. The MikroTik or other VPN gateway needs matching peers,
firewall permissions and return routing prepared separately.

## 2. Collect these details before installing

Ask your network administrator for this sheet. Do not guess the addresses.

| Detail | Meaning | Example only |
| --- | --- | --- |
| Office network | Private addresses the Linux server should reach. | 10.60.0.0/24 |
| Check computers | Reliable office devices that answer ping through every tunnel. | 10.60.0.10, 10.60.0.60 |
| Docker application network | The actual Docker subnet whose applications need office access. | 172.30.0.0/16 |
| VPN profiles | Matching client credentials and addresses for each gateway. | Two WireGuard .conf files |
| Application check | A real office application URL that answers successfully without interactive login. | http://10.60.0.60/health |
| Linux access | An independent SSH login, plus console access for recovery. | Your own server login |

These examples are not your production settings. The office, Docker and tunnel
networks must not overlap. One office IPv4 prefix and one Docker application
prefix are supported. If no application has a suitable HTTP check, an explicitly
chosen TCP check can test port access, but does not prove the application works.

The tested host was Ubuntu 24.04.4, kernel 6.8, Docker Engine 29.1.3 and Compose
2.40.3. Other Linux hosts need their own validation. This is not a Windows,
Docker Desktop, rootless Docker or Kubernetes installation guide.

Docker Engine with its Compose plugin, Python 3 and Git must already be installed.
Use [Docker's Ubuntu instructions](https://docs.docker.com/engine/install/ubuntu/)
for Docker. Have the host administrator review forwarding/firewall access and
confirm Docker provides the `DOCKER-USER` iptables chain. Do not disable the host
firewall to make a test pass.

## 3. Get the reviewed program files

The following candidate checkpoint passed its source checks. It is not a stable
release tag. Run on the separate test server:

```sh
sudo git clone --branch secure-management --single-branch \
  https://github.com/RomanAK92/vpn-failover-controller.git \
  /opt/vpn-failover-controller
cd /opt/vpn-failover-controller
sudo git checkout --detach ca507a2b259c777fd7e9ecc9394485bf3a6595d4
```

The checkout holds programs and examples. **Never put real keys into Git.**
`/root/vpn-settings` below holds private input settings; `/opt/vpn-system` will
hold the prepared installation. These are different folders.

## 4. Prepare your FIRST configuration

You do not need a running dashboard on this new server yet. Choose one route:

### Route A: you already have access to this candidate's dashboard elsewhere

1. Open **Profiles**. Enter the three network fields from your information sheet.
2. Add each WireGuard file, or enter each IPsec connection's structured settings.
3. Arrange the connections in preferred order. First means first choice.
4. Click **Validate & preview**. Correct any error; inspect the masked preview.
5. Click **Download private configuration**. The downloaded `vpn-private-config.tar`
   contains credentials. Transfer it privately to the new Linux server.

Inspect the archive's names before extraction. Use only the package generated by
this trusted wizard, with no unexpected paths or files. Replace the example
download path below with where you transferred your file:

```sh
sudo tar -tf /root/vpn-private-config.tar
sudo install -d -m 0700 /root/vpn-settings
sudo tar -xf /root/vpn-private-config.tar -C /root/vpn-settings
sudo chmod 600 /root/vpn-settings/*
```

### Route B: there is no dashboard yet — two existing WireGuard profiles

Start from the supplied two-tunnel template, in a new private folder:

```sh
cd /opt/vpn-failover-controller
sudo install -d -m 0700 /root/vpn-settings
sudo cp config/layouts/wireguard-2.json /root/vpn-settings/controller.json
sudo cp config/layouts/wireguard-peers.json /root/vpn-settings/peers.json
sudo cp config/examples/deployment.json /root/vpn-settings/deployment.json
```

Edit the three files with `sudo nano /root/vpn-settings/FILE_NAME`. In nano,
Ctrl+O then Enter saves; Ctrl+X closes. Keep JSON quotes and commas intact.

| Where | What to enter |
| --- | --- |
| controller.json: subnet and targets | Your office prefix and reliable check addresses. This template requires two successful checks; provide at least two reliable targets. |
| controller.json: first path address | Address from the first profile's Interface section. |
| controller.json: second path address | Address from the second profile's Interface section. |
| peers.json: peer-1 | First gateway's Endpoint IPv4, Endpoint port and Peer PublicKey. |
| peers.json: peer-2 | Second gateway's Endpoint IPv4, Endpoint port and Peer PublicKey. |
| peers.json: peer-3 and peer-4 | Remove these unused example entries for this two-profile setup. |
| deployment.json: app_subnet | Your real Docker application subnet. Leave publication null for outbound-only access. |

Create `/root/vpn-settings/wg-client-peer-1.key` and
`/root/vpn-settings/wg-client-peer-2.key` with sudo nano. Each contains **only**
the matching profile's Interface PrivateKey value, not the whole .conf file and
not the words `PrivateKey =`. Keep the original keys private; the gateway must
already recognize the corresponding client public key.

```sh
sudo chmod 600 /root/vpn-settings/*
```

Leave reserved routing IDs, interfaces and MTU/MSS at the reviewed defaults when
they are unused on this host. The first path in the paths array is preferred;
the numeric priority field is a routing identifier, not a reorder button.
This route needs administrator assistance if your profile includes DNS changes,
scripts, IPv6, multiple peers or unsupported settings. Do not silently discard
such options. [Other layouts and IPsec files](../CONFIGURATION.md) have their own
templates; the local profile wizard is the simpler route when available.

## 5. Validate and prepare the installation

Use your **real** application address/port/path in both commands. The example
`/health` URL must exist and return success through every configured tunnel:

```sh
cd /opt/vpn-failover-controller
sudo python3 management/bootstrap.py --config-dir /root/vpn-settings \
  --managed --application-address 10.60.0.60 \
  --application-port 80 --application-path /health
```

This first command only checks input and prints a plan. It starts nothing.
Resolve errors, then repeat with `--prepare`:

```sh
sudo python3 management/bootstrap.py --config-dir /root/vpn-settings \
  --managed --application-address 10.60.0.60 \
  --application-port 80 --application-path /health --prepare
```

It asks you to create your administrator username and passphrase. There is no
default login. Use at least 15 characters for the passphrase. It creates
`/opt/vpn-system` and refuses to overwrite an existing installation.

**Default: dashboard Apply is disabled.** To evaluate guarded web changes on a
NEW isolated installation, add `--enable-managed-changes` to **both** the plan
and prepare commands above, before creating the installation. This enables
matching engine and web gates; it does not start anything. Never use
`--enable-test-apply` as a normal installation workaround. Preparation is not an
upgrade command and does not change an existing installation's control policy.

## 6. Check the host, then start

Only on the prepared separate host, have the administrator enable required
forwarding and load the kernel support for the protocols actually used:

```sh
printf 'net.ipv4.ip_forward=1\n' | sudo tee /etc/sysctl.d/90-vpn-router.conf
sudo sysctl -p /etc/sysctl.d/90-vpn-router.conf
sudo modprobe wireguard
```

For an IPsec layout, also load `xfrm_interface` as required by your kernel.
Do not change global reverse-path filtering or existing firewall rules blindly.

```sh
cd /opt/vpn-system
sudo docker compose --project-name vpn-system config
sudo docker compose --project-name vpn-system build
sudo docker compose --project-name vpn-system run --rm --no-deps \
  --volume /root/vpn-settings:/etc/vpn:ro \
  --entrypoint python3 vpn-router /app/doctor.py
```

Do not start if the doctor reports ERROR. Review every WARN. Configuration
validation is not a tunnel or application test. The extra read-only volume is
needed because the managed engine normally reads its private version store,
while doctor.py reads /etc/vpn. It is only for this one preflight container.
Once preflight passes:

```sh
sudo docker compose --project-name vpn-system up -d
sudo docker compose --project-name vpn-system ps
sudo docker compose --project-name vpn-system logs --since 10m vpn-router
```

Never start two controllers owning the same routes/interfaces/firewall resources.
Do not paste settings, credentials or full logs into public issues.

## 7. Open your dashboard

Run this on **your own computer**, replacing the uppercase SSH details:

```sh
ssh -p YOUR_SSH_PORT -L 8787:127.0.0.1:8787 YOUR_USER@YOUR_SERVER
```

Keep SSH open. In that computer's browser visit **http://127.0.0.1:8787** and use
the account you created in step 5. Here 127.0.0.1 means your own computer; the
SSH connection carries requests to the server's private web service. If the
SSH forward closes, that browser address stops working.

For direct VPN/LAN access, use the
[private HTTPS procedure](README.md#open-the-page-privately), a specific address
owned by the Linux host, trusted certificates and explicit allowed client ranges.
Example HTTPS port: 8443. Do not expose the HTTP backend to the public internet
or bypass certificate warnings.

## 8. What each dashboard function is for

### Overview — see what is happening

| Item | Plain meaning |
| --- | --- |
| Private network connected | The current monitoring reports a healthy selected connection. Still test your real application. |
| Active | This road carries the selected office traffic. |
| Ready / standby | Healthy spare road; it is not currently selected. |
| Probe failing | One or more configured checks failed; thresholds determine switching. |
| Monitoring unavailable | Fresh trustworthy status is missing. Old status must not be treated as current health. |
| Priority 1, 2, 3, 4 | Normal preference order, not simultaneous load balancing. |
| Answered / no answer | Result of a configured reachability check. It is not an authenticated business transaction. |
| Recovery stability | Remaining healthy rounds before a recovered preferred road becomes eligible. |
| What happened? | Readable status/switch observations, not complete daemon logs. |
| Show events for | Filter history to one road or see every road. |

### Profiles — build and privately save a configuration

| Field/button | What it does |
| --- | --- |
| Office network | Private destination subnet that the VPN should reach. |
| Reliable office computers | Ping targets used to judge whether a road works. |
| Docker application network | Source subnet of containers that need the office VPN. |
| Add WireGuard profile | Add a road by choosing a supported client .conf file or pasting it. Reading the file is local until explicit Save. |
| Add IPsec settings | Add IKEv2 gateway IPv4, client tunnel address, local/remote identity and matching shared secret. Arbitrary IPsec files/certificates/EAP are not imported. |
| Higher / lower priority | Move a road earlier/later in the preference order. |
| Remove | Remove that road from the form, not from the running VPN. |
| Validate & preview | Check the entered settings locally and show a key-masked summary. No traffic changes. |
| Green check / red X | Locally valid / error below. Neither is an application health verdict. |
| Download private configuration | Export settings and secrets for a separate installation. It does not start a VPN. |
| Clear profile secrets | Clear the form. Downloaded files and previously saved server drafts still exist. |
| Draft name | A readable name for this stored configuration, such as Office connection. |
| Save reviewed settings | Upload the checked settings and credentials to private administrator draft storage. No Apply. |
| Show saved drafts | Reload saved/archived copies; summaries hide keys. |
| Continue to VPN review | Open VPN changes with that draft already selected; no preparation or traffic change. |
| Archive / restore draft | Hide an unused saved copy in the archive / bring it back. Neither deletes it or switches traffic. |

### VPN changes — review, apply temporarily, then keep or undo

| Field/button | What it does |
| --- | --- |
| Refresh engine status | Retrieve the current engine/change/readiness state. |
| Configuration already prepared for review | Choose an immutable settings version already staged for the engine. This is different from a saved draft. |
| Load saved configurations | Load private drafts that can be prepared for review. |
| Choose a saved draft | Choose the saved input copy; the nearby message explains the next step. |
| Prepare for review | Create an engine settings version; no live traffic changes. Different tunnel counts are blocked here. |
| Review what will change | Ask the engine for differences and full network-footprint compatibility. Same counts alone are insufficient. |
| Apply reviewed settings | Start a guarded change with a confirmation deadline. May briefly interrupt the VPN. Requires administrator reauthentication and healthy prerequisites. |
| Keep these settings | After testing your application, re-enter the passphrase and confirm before the timer ends. The engine also checks all required paths/application. |
| Undo this change | Request the previous confirmed settings. Recovery is complete only after fresh checks pass. |
| Archive / restore prepared settings | Move an unused engine version out of/into the review list. Active/recovery-referenced versions are protected. |
| Settings reference | Automatically filled technical ID for troubleshooting; normally leave it alone. |
| Preferred road | Temporarily prefer a healthy connection. Normal fallback rules still apply. |
| Temporarily exclude | Keep checking a road but exclude it from traffic selection during maintenance. This does not disable a router peer. |
| Automatically return after | Duration of the temporary request, in seconds; default 300 means five minutes. |
| Request temporary selection | Submit that timed request. Acknowledgement is not proof that traffic already switched; check Overview. |
| Return to automatic priority | Clear the temporary request; healthy recovery thresholds still apply. |

Sensitive actions clear the entered administrator passphrase. Re-enter it before
the next action. After Apply, check your real application and confirm within the
displayed countdown, normally three minutes. If you do not confirm, recovery is
requested automatically; the engine must prove the previous setup works again.
Unsupported WireGuard scripts such as PostUp are rejected and never executed.

**Example:** your installation has four tunnels, and Office connection contains
one. The draft can be saved/exported but cannot replace that installation through
this workflow. A separate migration is required. Initial installation supports
one to four tunnels; this is not a live add/remove-tunnel wizard.

### Accounts — control who can use the page

| Field/button | What it does |
| --- | --- |
| Existing accounts | Show account name, Administrator/Viewer role and Active/Disabled state. |
| Refresh accounts and security events | Reload the account list and readable activity. |
| Security events | Sign-in/account/control-request audit history; scroll inside the bounded box for older events. |
| Create account | Add a separate login with its own passphrase. |
| Viewer role | See monitoring and prepare/download own profiles locally; cannot operate the engine, read private drafts, manage users or download admin support. |
| Administrator role | Access privileged functions, still subject to reauthentication and engine safeguards. |
| Reset existing account | Change its passphrase and revoke its sessions. It does not silently re-enable a disabled user. |
| Disable / re-enable | Block new sign-ins without deleting the account / allow sign-in again. |
| Permanently delete | Remove the account and its sessions after explicit confirmation and exact-name entry. No recycle bin; security history stays. |
| Download anonymous support report | Export numbered path/health counters for support without keys, IPs, account/path names or raw logs. |
| Sign out | End your session. Back/refresh must not restore protected access. |

You cannot disable/delete yourself or the last active administrator. Never reuse
a shared demonstration password for an installation.

## 9. Confirm the installation actually works

Check Overview shows fresh status and the expected active/standby roads. Test
real traffic from the application container to the office application. On an
isolated setup, verify each intended backup, recovery and access to the dashboard
or independent SSH. Green containers alone are not proof of application access.

Default installs have Apply disabled; that is expected. Initial configured VPN
traffic can still operate. To change the number/names/resources of live paths,
plan a separate migration instead of defeating the review checks.

## 10. Upgrades, backups and stopping

This guide installs a new candidate system. It does not migrate an older custom
wireguard-router, your production installation or every previous release.
Bootstrap refuses to overwrite an installation. Do not use the root legacy
Compose workflow and the managed workflow as two simultaneous owners.

Encrypted settings backup/restore is a separate administrator procedure in
[the management guide](README.md#encrypted-offline-backup). It excludes accounts,
certificates, applications, old binaries and logs. Those need separate private
backups. Restore into a new directory with a new administrator; it starts nothing.

Stopping containers is not complete network cleanup. Preserve recovery evidence
and use a reviewed ownership-scoped cleanup procedure; do not delete private data
or unrelated Docker resources to tidy the server.
